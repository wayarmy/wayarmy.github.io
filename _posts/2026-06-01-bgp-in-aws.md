## 1. Giới thiệu — Cầu nối giữa hai thế giới

Hãy tưởng tượng công ty bạn có **văn phòng chính** (On-Premises Data Center) và **chi nhánh trên cloud** (AWS). Hai bên cần giao tiếp với nhau liên tục — nhân viên ở văn phòng cần truy cập ứng dụng trên cloud, và ngược lại.

Bạn có 2 cách kết nối:
- **VPN qua Internet** = Gửi thư qua bưu điện công cộng — rẻ, nhưng chậm và không đảm bảo
- **Direct Connect** = Đường dây điện thoại riêng — đắt hơn, nhưng nhanh, ổn định, riêng tư

Dù chọn cách nào, cả hai bên cần **thống nhất đường đi** — "từ mạng A đến mạng B đi qua đâu?" Đây chính là vai trò của **BGP trong AWS**.

### Tại sao BGP quan trọng trong AWS?

| Service | Dùng BGP cho |
|---|---|
| Direct Connect | Trao đổi routes giữa on-prem và AWS |
| Site-to-Site VPN | Dynamic routing (thay vì static) |
| Transit Gateway | Route propagation giữa VPCs và on-prem |
| TGW Connect | GRE + BGP cho SD-WAN integration |
| Global Accelerator | Anycast BGP announcement |

### AWS BGP Quick Facts

```
AWS BGP Parameters:
- AWS ASN: 64512 (default private) hoặc custom (64512-65534, 4200000000-4294967294)
- Customer ASN: Any valid public or private ASN
- Protocol: BGP-4 over TCP/179
- Session type: eBGP (always — AWS và customer luôn khác AS)
- Max prefixes: 100 (per BGP session, DX private/transit VIF)
- Max prefixes: 1000 (public VIF)
- Supported: IPv4 + IPv6 (dual-stack)
- MD5 Auth: Supported
- BFD: Supported on Direct Connect
- Graceful Restart: Supported
- Multipath: Supported (ECMP)
```

## 2. AWS Direct Connect là gì? — Kết nối dành riêng

### Phép so sánh đời thường

Tưởng tượng bạn đang ở Hà Nội và cần gửi tài liệu mật đến chi nhánh ở Đà Nẵng mỗi ngày:

- **Internet VPN** = Gửi qua grab/shipper công cộng. Rẻ, nhưng: đường đông thì chậm, tài liệu đi qua nhiều tay, rủi ro bị xem trộm (dù đã bỏ phong bì niêm phong).
- **Direct Connect** = Thuê đường truyền riêng (leased line). Đắt hơn, nhưng: luôn đúng giờ, không ai khác dùng chung, bảo mật vật lý.

### Kiến trúc Direct Connect

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                   │
│  Customer         DX Location          AWS                       │
│  Data Center      (Colocation)         Region                    │
│                                                                   │
│  ┌─────────┐     ┌────────────┐      ┌──────────────┐           │
│  │Customer │     │  Customer  │      │              │           │
│  │Router   │─────│  Router/   │──────│ AWS Router   │           │
│  │(CE)     │     │  Cage      │      │ (DX Endpoint)│           │
│  └─────────┘     └────────────┘      └──────┬───────┘           │
│       │           Cross-Connect              │                   │
│       │           (fiber patch)              │                   │
│   On-Prem                              ┌────┴──────┐            │
│   Network                              │ DX Gateway│            │
│                                        └────┬──────┘            │
│                                             │                    │
│                                    ┌────────┼────────┐          │
│                                    │        │        │          │
│                                  VGW      TGW      VGW         │
│                                  VPC-1           VPC-2          │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘

Components:
1. Connection: Physical fiber (1G/10G/100G) tại DX Location
2. Virtual Interface (VIF): Logical connection trên physical fiber
3. DX Gateway: Regional construct kết nối VIFs với VGW/TGW
4. VGW/TGW: Endpoint trong VPC/network
```

### Virtual Interface Types

```
┌─────────────────────────────────────────────────────────────────┐
│ VIF Type    │ Purpose           │ Connects to     │ BGP Scope    │
├─────────────┼───────────────────┼─────────────────┼──────────────┤
│ Private VIF │ Access VPC        │ VGW hoặc DXGW   │ VPC CIDRs    │
│             │ (private IPs)     │                 │ (max 100     │
│             │                   │                 │  prefixes)   │
├─────────────┼───────────────────┼─────────────────┼──────────────┤
│ Transit VIF │ Access multiple   │ DXGW → TGW      │ TGW attached │
│             │ VPCs via TGW      │                 │ routes       │
│             │                   │                 │ (max 100)    │
├─────────────┼───────────────────┼─────────────────┼──────────────┤
│ Public VIF  │ Access AWS public │ AWS Public      │ All AWS      │
│             │ services (S3,     │ endpoints       │ public IPs   │
│             │ DynamoDB, etc.)   │                 │ (max 1000)   │
└─────────────┴───────────────────┴─────────────────┴──────────────┘
```

### BGP Session trên Direct Connect

```
Physical Connection: 10Gbps Dedicated
  │
  ├── VLAN 100: Private VIF → VGW (VPC Production)
  │   BGP Session: 169.254.10.0/30
  │   Customer: 169.254.10.2 (AS 65000)
  │   AWS:      169.254.10.1 (AS 64512)
  │
  ├── VLAN 200: Transit VIF → DXGW → TGW
  │   BGP Session: 169.254.20.0/30
  │   Customer: 169.254.20.2 (AS 65000)
  │   AWS:      169.254.20.1 (AS 64512)
  │
  └── VLAN 300: Public VIF → AWS Public Services
      BGP Session: 169.254.30.0/30 (or public IPs)
      Customer: 169.254.30.2 (AS 65000)
      AWS:      169.254.30.1 (AS 7224)
      
⚠️ Public VIF uses AWS public ASN (7224) 
   Private/Transit VIF uses configured ASN (default 64512)
```

### Trong thực tế

**Cấu hình BGP trên Customer Router (Cisco):**
```cisco
! Private VIF BGP configuration
router bgp 65000
 bgp log-neighbor-changes
 
 ! Private VIF - access VPC
 neighbor 169.254.10.1 remote-as 64512
 neighbor 169.254.10.1 description AWS-DX-PrivateVIF
 neighbor 169.254.10.1 password MD5_SECRET
 
 address-family ipv4 unicast
  ! Advertise on-prem networks to AWS
  network 10.0.0.0 mask 255.255.0.0
  network 172.16.0.0 mask 255.255.0.0
  
  ! Accept AWS VPC routes
  neighbor 169.254.10.1 activate
  neighbor 169.254.10.1 route-map AWS_IN in
  neighbor 169.254.10.1 route-map AWS_OUT out
  neighbor 169.254.10.1 prefix-list ACCEPT_AWS in
  neighbor 169.254.10.1 maximum-prefix 100

! Route maps
route-map AWS_IN permit 10
 set local-preference 200    ! Prefer DX over VPN

route-map AWS_OUT permit 10
 match ip address prefix-list ON_PREM_ROUTES
 ! Only advertise authorized on-prem prefixes

! Prefix lists
ip prefix-list ON_PREM_ROUTES permit 10.0.0.0/16
ip prefix-list ON_PREM_ROUTES permit 172.16.0.0/16
ip prefix-list ACCEPT_AWS permit 10.100.0.0/16    ! VPC CIDR
```

## 3. BGP Communities trong AWS Direct Connect

### Mini-example: Hệ thống tag hành lý sân bay

Khi bạn gửi hành lý ở sân bay, nhân viên dán **tag** để chỉ định:
- Tag xanh: "Chuyển đến terminal quốc tế"
- Tag đỏ: "Ưu tiên xử lý"  
- Tag vàng: "Hành lý dễ vỡ — cẩn thận"

BGP Communities hoạt động tương tự — đây là **tags gắn vào routes** để AWS (và bạn) biết phải xử lý route đó như thế nào.

### AWS Direct Connect BGP Communities

```
┌─────────────────────────────────────────────────────────────────┐
│          AWS BGP Communities cho INBOUND Traffic                  │
│    (Customer gắn vào routes advertised TO AWS)                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│ Local Preference Communities (Private/Transit VIF):              │
│                                                                   │
│ 7224:7100 = Low Preference (LP = low)                           │
│ 7224:7200 = Medium Preference (LP = medium)                      │
│ 7224:7300 = High Preference (LP = high)  ← Default nếu không tag│
│                                                                   │
│ Ví dụ: 2 DX connections (primary + backup)                       │
│ - Primary DX: Advertise routes với 7224:7300 (high pref)        │
│ - Backup DX: Advertise routes với 7224:7100 (low pref)          │
│ → AWS prefer path qua Primary DX                                │
│                                                                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│ Public VIF Scope Communities (Customer → AWS):                   │
│                                                                   │
│ 7224:9100 = Advertise to local AWS Region only                  │
│ 7224:9200 = Advertise to continent only                         │
│ 7224:9300 = Advertise globally (all AWS Regions)                │
│                                                                   │
│ Ví dụ: Bạn ở Singapore DX, muốn route chỉ valid ở Asia:        │
│ → Gắn community 7224:9200                                       │
│                                                                   │
└─────────────────────────────────────────────────────────────────┘
```

```
┌─────────────────────────────────────────────────────────────────┐
│          AWS BGP Communities cho OUTBOUND Traffic                 │
│    (AWS gắn vào routes advertised TO Customer)                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                   │
│ Private/Transit VIF — AWS advertises VPC routes:                 │
│ No specific communities (routes from VPC/TGW route tables)       │
│                                                                   │
│ Public VIF — AWS advertises public prefixes:                     │
│                                                                   │
│ 7224:8100 = Routes from same Region as DX connection            │
│ 7224:8200 = Routes from same Continent                          │
│ 7224:8300 = Global routes (other continents)                    │
│                                                                   │
│ Ví dụ: Customer tại Singapore DX nhận:                           │
│ - ap-southeast-1 routes: tagged 7224:8100                       │
│ - ap-northeast-1 routes: tagged 7224:8200                       │
│ - us-east-1 routes: tagged 7224:8300                            │
│                                                                   │
│ Customer có thể filter:                                          │
│ - Accept 7224:8100 qua DX Singapore (local)                    │
│ - Accept 7224:8200 qua DX Singapore (continental)              │
│ - Reject 7224:8300 (global — dùng Internet thay thế)           │
│                                                                   │
│ NO_EXPORT: AWS gắn NO_EXPORT cho tất cả Public VIF routes       │
│ → Customer KHÔNG ĐƯỢC re-advertise ra Internet!                  │
│                                                                   │
└─────────────────────────────────────────────────────────────────┘
```

### Ví dụ thực tế: Active/Passive DX với Communities

```cisco
! Scenario: 2 DX connections cho HA
! DX-1 (Tokyo): Primary
! DX-2 (Singapore): Backup

! Customer Router at DX-1 (Tokyo) - PRIMARY:
route-map TO_AWS_PRIMARY permit 10
 match ip address prefix-list ON_PREM_ROUTES
 set community 7224:7300    ! High preference
 ! AWS will prefer this path (highest local-pref)

! Customer Router at DX-2 (Singapore) - BACKUP:
route-map TO_AWS_BACKUP permit 10
 match ip address prefix-list ON_PREM_ROUTES
 set community 7224:7100    ! Low preference
 ! AWS will use this only when DX-1 is down

! Alternative: AS-PATH Prepending (cũng hoạt động)
route-map TO_AWS_BACKUP permit 10
 match ip address prefix-list ON_PREM_ROUTES
 set as-path prepend 65000 65000 65000
 ! Longer path = less preferred by AWS
```

### Filtering AWS routes nhận được

```cisco
! Trên customer router, filter routes từ AWS:

! Chỉ accept routes từ VPC CIDRs đã biết
ip prefix-list ACCEPT_FROM_AWS seq 10 permit 10.100.0.0/16    ! VPC Prod
ip prefix-list ACCEPT_FROM_AWS seq 20 permit 10.200.0.0/16    ! VPC Dev
ip prefix-list ACCEPT_FROM_AWS seq 30 permit 10.250.0.0/16    ! VPC Shared
ip prefix-list ACCEPT_FROM_AWS seq 100 deny 0.0.0.0/0 le 32  ! Deny all else

! Filter based on communities (Public VIF)
ip community-list standard LOCAL_REGION permit 7224:8100
ip community-list standard CONTINENTAL permit 7224:8200

route-map FROM_AWS_PUBLIC permit 10
 match community LOCAL_REGION
 set local-preference 200    ! Prefer local region routes

route-map FROM_AWS_PUBLIC permit 20
 match community CONTINENTAL
 set local-preference 100    ! Lower pref for continental

route-map FROM_AWS_PUBLIC deny 30
 ! Deny global routes (use Internet instead)
```

## 4. Transit Gateway và BGP — Multi-VPC Routing

### Mini-example: Bến xe trung tâm

Tưởng tượng Transit Gateway như **bến xe trung tâm** của thành phố:
- Mỗi **VPC** = một quận/huyện
- Mỗi **Direct Connect** = một tuyến xe liên tỉnh
- Mỗi **VPN** = một tuyến xe nhỏ hơn
- **TGW Route Table** = bảng lịch trình xe — xe nào chạy đến quận nào

Tất cả xe (traffic) phải qua bến xe trung tâm (TGW) để đi từ quận này sang quận khác.

### Transit Gateway Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│                     Transit Gateway                              │
│                                                                   │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │              TGW Route Table "Production"                │   │
│   │                                                         │   │
│   │  10.100.0.0/16 → VPC-Prod attachment                    │   │
│   │  10.200.0.0/16 → VPC-Dev attachment                     │   │
│   │  172.16.0.0/12 → DX Gateway attachment (propagated)     │   │
│   │  0.0.0.0/0     → VPC-Egress attachment                  │   │
│   └─────────────────────────────────────────────────────────┘   │
│                                                                   │
│   Attachments:                                                    │
│   ├── VPC-Prod (10.100.0.0/16)                                  │
│   ├── VPC-Dev (10.200.0.0/16)                                   │
│   ├── VPC-Shared (10.150.0.0/16)                                │
│   ├── DX Gateway (→ On-Premises 172.16.0.0/12)                  │
│   ├── VPN (→ Branch Office 192.168.0.0/16)                      │
│   └── TGW Peering (→ Other Region TGW)                          │
│                                                                   │
└─────────────────────────────────────────────────────────────────┘
```

### Route Propagation và BGP

```
TGW Route Types:
1. Static Routes: Manually added (highest priority)
2. Propagated Routes: Dynamically learned from attachments

Route Sources:
- VPC Attachment: Propagates VPC CIDR automatically
- DX Gateway: Propagates routes received via BGP from on-prem
- VPN: Propagates routes received via BGP (or static)
- TGW Connect: Propagates routes from BGP peer (SD-WAN)
- TGW Peering: Routes from peered TGW

Route Priority (khi conflict):
1. Static route (longest prefix match)
2. VPC attachment (local VPC CIDR)
3. DX Gateway (BGP from on-prem)
4. VPN (BGP from remote site)
5. TGW Peering

Khi multiple routes cùng prefix:
- Prefer shortest AS-PATH
- Prefer DX over VPN
- ECMP nếu routes tương đương
```

### TGW Route Selection Algorithm

```
AWS Transit Gateway Path Selection:

1. Longest Prefix Match (MOST IMPORTANT)
   - /24 always beats /16 regardless of source
   
2. Static > Propagated
   - Static route ALWAYS wins over propagated route (same prefix)
   
3. For propagated routes (same prefix, same length):
   a. VPC route (directly attached)
   b. Direct Connect Gateway route
   c. VPN route (Site-to-Site)
   d. TGW Peering route
   
4. For same attachment type:
   a. Shortest AS-PATH
   b. If same AS-PATH: ECMP (multi-path)

5. ECMP Support:
   - Up to 50 equal-cost paths
   - Between same attachment type
   - DX: ECMP across multiple DX connections (via DXGW)
   - VPN: ECMP across VPN tunnels

⚠️ QUAN TRỌNG:
- TGW KHÔNG support MED, LOCAL_PREF, Weight
- Only AS-PATH length matters for DX/VPN propagated routes
- Communities are NOT evaluated by TGW for path selection
```

### Transit VIF vs Private VIF

```
┌────────────────────────────────────────────────────────────────┐
│                   Private VIF                                    │
│                                                                  │
│  Customer ──DX── DXGW ──── VGW (attached to 1 VPC)            │
│                                                                  │
│  Pros:                                                           │
│  - Simple setup                                                  │
│  - Direct path to VPC                                           │
│  - No TGW cost                                                  │
│                                                                  │
│  Cons:                                                           │
│  - 1 VIF per VPC (or max 10 VGWs per DXGW)                     │
│  - No transitive routing between VPCs                           │
│  - Max 100 prefixes advertised to customer                      │
│                                                                  │
├────────────────────────────────────────────────────────────────┤
│                   Transit VIF                                    │
│                                                                  │
│  Customer ──DX── DXGW ──── TGW ──── Multiple VPCs             │
│                                                                  │
│  Pros:                                                           │
│  - 1 VIF → access ALL VPCs via TGW                             │
│  - Transitive routing (VPC-to-VPC via TGW)                      │
│  - Scalable (thousands of VPCs)                                 │
│  - Centralized routing control                                  │
│                                                                  │
│  Cons:                                                           │
│  - TGW data processing charges                                  │
│  - Additional hop (slightly higher latency)                     │
│  - Max 20 prefixes FROM AWS TO customer (DXGW→on-prem)         │
│    (Can be increased to 100 with support request)               │
│                                                                  │
└────────────────────────────────────────────────────────────────┘
```

### Trong thực tế

**Multi-Region DX with TGW:**
```
┌──────────────────┐         ┌──────────────────┐
│  On-Premises     │         │    AWS           │
│                  │         │                  │
│                  │  DX-1   │ ┌─────────────┐  │
│  ┌──────┐       │────────→│ │ TGW Tokyo   │  │
│  │ Core │       │         │ │  ├─ VPC-1    │  │
│  │Router│       │         │ │  ├─ VPC-2    │  │
│  │      │       │         │ │  └─ TGW Peer │  │
│  │      │       │  DX-2   │ └──────┬──────┘  │
│  │      │       │────────→│        │ TGW      │
│  └──────┘       │         │        │ Peering  │
│                  │         │ ┌──────┴──────┐  │
│                  │         │ │TGW Singapore│  │
│                  │         │ │  ├─ VPC-3   │  │
│                  │         │ │  └─ VPC-4   │  │
│                  │         │ └─────────────┘  │
└──────────────────┘         └──────────────────┘

BGP Advertisement from On-Prem:
- DX-1 (Tokyo): 10.0.0.0/8 with NO prepend (primary for Tokyo VPCs)
- DX-2 (Singapore): 10.0.0.0/8 with prepend x2 (primary for SG VPCs)

BGP from AWS:
- Tokyo TGW advertises: 10.100.0.0/16, 10.200.0.0/16 (Tokyo VPCs)
- Singapore TGW advertises: 10.300.0.0/16, 10.400.0.0/16 via TGW peering

Customer routing decision:
- Traffic to 10.100.0.0/16 → via DX-1 (shortest path)
- Traffic to 10.300.0.0/16 → via DX-2 (or DX-1 depending on peering setup)
```

## 5. Site-to-Site VPN với BGP — Dynamic VPN

### Mini-example: GPS tự tìm đường thay vì bản đồ giấy

- **Static VPN** = Bản đồ giấy — bạn phải tự vẽ đường đi, nếu đường thay đổi phải vẽ lại
- **Dynamic VPN (BGP)** = GPS — tự động cập nhật đường đi, nếu có đường mới → tự thêm

### VPN BGP Configuration

```
AWS Site-to-Site VPN:
- 2 tunnels per VPN connection (HA)
- Each tunnel = 1 BGP session
- AWS side ASN: 64512 (default) or custom
- Customer side ASN: your AS number
- Inside tunnel CIDR: 169.254.x.x/30 (auto-assigned or custom)

Tunnel 1:
  Outside IP (AWS): 54.x.x.x
  Outside IP (Customer): Your public IP
  Inside IP (AWS): 169.254.100.1/30
  Inside IP (Customer): 169.254.100.2/30
  BGP Peer: 169.254.100.1 (AS 64512)
  
Tunnel 2:
  Outside IP (AWS): 52.x.x.x
  Inside IP (AWS): 169.254.100.5/30
  Inside IP (Customer): 169.254.100.6/30
  BGP Peer: 169.254.100.5 (AS 64512)
```

```cisco
! Customer Router Configuration (Cisco):

! Tunnel 1
interface Tunnel1
 ip address 169.254.100.2 255.255.255.252
 tunnel source GigabitEthernet0/0
 tunnel destination 54.x.x.x
 tunnel mode ipsec ipv4
 tunnel protection ipsec profile AWS_IPSEC_PROFILE

! Tunnel 2
interface Tunnel2
 ip address 169.254.100.6 255.255.255.252
 tunnel source GigabitEthernet0/0
 tunnel destination 52.x.x.x
 tunnel mode ipsec ipv4
 tunnel protection ipsec profile AWS_IPSEC_PROFILE

! BGP Configuration
router bgp 65000
 neighbor 169.254.100.1 remote-as 64512
 neighbor 169.254.100.1 description AWS-VPN-Tunnel1
 neighbor 169.254.100.5 remote-as 64512
 neighbor 169.254.100.5 description AWS-VPN-Tunnel2
 
 address-family ipv4
  network 10.0.0.0 mask 255.255.0.0    ! On-prem network
  neighbor 169.254.100.1 activate
```

## 6. AS-PATH Prepending trong AWS — Traffic Engineering

### Mini-example: Làm đường dài hơn để ít xe đi

Tưởng tượng bạn quản lý 2 con đường vào thành phố:
- **Đường A** (DX Primary): 3 ngã tư → xe prefer đường này
- **Đường B** (VPN Backup): 3 ngã tư → cũng được prefer

Để ít xe đi đường B, bạn **thêm ngã tư giả** vào đường B:
- **Đường B** trở thành: 6 ngã tư → xe tự động avoid (dài quá!)

AS-PATH Prepending làm chính xác điều này — thêm AS number vào path để làm nó "dài hơn" và ít được prefer.

### Cách AS-PATH Prepending hoạt động

```
Scenario: AS 65000 muốn inbound traffic prefer DX-1 over DX-2

Không prepend:
DX-1 advertises: 10.0.0.0/16 → AS_PATH = 65000
DX-2 advertises: 10.0.0.0/16 → AS_PATH = 65000
→ AWS thấy cả 2 paths BẰNG NHAU (ECMP hoặc random)

Với prepend trên DX-2:
DX-1 advertises: 10.0.0.0/16 → AS_PATH = 65000
DX-2 advertises: 10.0.0.0/16 → AS_PATH = 65000 65000 65000
→ AWS prefer DX-1 (AS-PATH ngắn hơn: length 1 vs 3)

⚠️ AWS LIMITATION:
- AWS accepts AS-PATH prepending (evaluates in TGW/VGW path selection)
- AWS prefers: Shortest AS-PATH > Longest
- AWS ALSO prefers: DX > VPN (regardless of AS-PATH!)
- AS-PATH prepending useful between:
  - Multiple DX connections (same type)
  - Multiple VPN connections (same type)
  - NOT between DX and VPN (DX always wins)
```

### Best Practices cho AS-PATH Prepending

```
1. Prepend tối đa 3 lần (diminishing returns sau đó)
   - 1 prepend: Đủ cho most path selection
   - 3 prepend: Maximum practical impact
   - > 3: Wasted, doesn't help

2. Chỉ prepend AS NUMBER CỦA MÌNH
   - NEVER prepend AS khác (security violation, some ISPs filter)
   - AWS verifies first AS in path matches peer AS

3. Không dùng prepend giữa DX và VPN
   - DX ALWAYS preferred by TGW over VPN (built-in)
   - Prepend chỉ useful giữa multiple DX hoặc multiple VPN

4. Combine với Communities cho best results
   - AS-PATH prepend: Control inter-region preference
   - BGP Communities: Control intra-DX-gateway preference
```

### Ví dụ Multi-Region với Prepending


## 7. TGW Connect — SD-WAN Integration

### Mini-example: Dịch vụ xe buýt express

TGW Connect giống **xe buýt express** mà không dừng mọi trạm:
- Thay vì mỗi chi nhánh kết nối riêng VPN vào TGW
- Một SD-WAN appliance (trên EC2) tập hợp tất cả routes
- Kết nối vào TGW qua GRE tunnel + BGP (nhanh, hiệu quả)

### TGW Connect Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                   │
│  Branch Sites        SD-WAN Hub (EC2)        AWS TGW             │
│                                                                   │
│  Branch-1 ──┐       ┌──────────────┐      ┌─────────────┐      │
│  Branch-2 ──┼──SD-WAN│  SD-WAN     │ GRE  │ TGW Connect │      │
│  Branch-3 ──┘ Overlay│  Controller │══════│ Peer        │      │
│                       │  (EC2)      │ BGP  │             │      │
│                       └──────────────┘      └──────┬──────┘      │
│                       VPC (Transport)              │             │
│                                                    │             │
│                                              ┌─────┴─────┐      │
│                                              │    TGW    │      │
│                                              └─┬───┬───┬─┘      │
│                                                │   │   │         │
│                                              VPC VPC VPC        │
│                                                                   │
└─────────────────────────────────────────────────────────────────┘

How it works:
1. SD-WAN appliance in VPC learns routes from all branches
2. Establishes GRE tunnel to TGW (via TGW Connect attachment)
3. BGP session over GRE: Advertises branch routes to TGW
4. TGW propagates routes to other VPCs/attachments
5. Return traffic: TGW → GRE → SD-WAN → Branch
```

### TGW Connect BGP

```
TGW Connect specifications:
- Protocol: GRE encapsulation + BGP peering
- BGP: Standard eBGP over GRE tunnel
- Max Connect peers per attachment: 4
- Each peer: 2 BGP sessions (redundancy)
- Throughput: Up to 5 Gbps per Connect peer
- Total: Up to 20 Gbps per Connect attachment (4 × 5 Gbps)
- MP-BGP supported: IPv4, IPv6

Use cases:
1. SD-WAN integration (Cisco SD-WAN, VMware SD-WAN, etc.)
2. Third-party routing appliance on EC2
3. High-throughput requirements (vs 1.25G per VPN tunnel)
4. GRE tunnel requirement (some SD-WAN solutions need GRE)
```

```
! SD-WAN appliance (on EC2) BGP config:

! GRE Tunnel to TGW
interface Tunnel1
 ip address 169.254.10.2 255.255.255.252
 tunnel source 10.0.1.100    ! EC2 private IP
 tunnel destination 10.0.1.200    ! TGW Connect endpoint
 tunnel mode gre ip

! BGP to TGW
router bgp 65000
 neighbor 169.254.10.1 remote-as 64512    ! TGW ASN
 address-family ipv4
  ! Advertise branch routes learned via SD-WAN
  network 192.168.1.0 mask 255.255.255.0    ! Branch-1
  network 192.168.2.0 mask 255.255.255.0    ! Branch-2
  network 192.168.3.0 mask 255.255.255.0    ! Branch-3
  neighbor 169.254.10.1 activate
```

```
│                                                             │
│ Traffic Engineering:                                        │
│ ▸ Outbound (On-Prem → AWS): LOCAL_PREF trên customer router│
│ ▸ Inbound (AWS → On-Prem): AS-PATH prepend + Communities  │
│ ▸ Communities: 7224:7100/7200/7300 (low/med/high pref)     │
│ ▸ TGW prefers: DX > VPN (built-in, no config needed)      │
│                                                             │
│ Transit Gateway Route Selection:                            │
│ ▸ Longest prefix match FIRST                              │
│ ▸ Static > Propagated                                      │
│ ▸ VPC > DX > VPN > Peering (for same prefix)             │
│ ▸ Shortest AS-PATH (for same attachment type)             │
│ ▸ ECMP supported (up to 50 paths)                         │
│                                                             │
│ High Availability:                                          │
│ ▸ Minimum: 2 DX connections at different locations         │
│ ▸ Recommended: 4 connections (2 locations × 2 connections) │
│ ▸ Emergency: VPN backup (lower bandwidth)                  │
│ ▸ BFD: Enable for sub-second failover detection           │
│                                                             │
│ Key Limitations:                                            │
│ ▸ TGW doesn't evaluate MED, LOCAL_PREF, Weight            │
│ ▸ Transit VIF: Default 20 prefixes from AWS to customer   │
│ ▸ VPN: Max 1.25 Gbps per tunnel                          │
│ ▸ DX: BGP hold timer 90s default (use BFD!)              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Design Decision Matrix

```
┌──────────────────────────────────────────────────────────────┐
│ Scenario                    │ Recommended Design              │
├─────────────────────────────┼─────────────────────────────────┤
│ 1 VPC, low traffic         │ Private VIF + VGW               │
│ Multiple VPCs, 1 region    │ Transit VIF + TGW               │
│ Multiple VPCs, multi-region│ Transit VIF + TGW + TGW Peering│
│ SD-WAN integration         │ TGW Connect (GRE + BGP)        │
│ Low-cost backup            │ Site-to-Site VPN (BGP dynamic) │
│ Maximum resiliency         │ 4 DX (2 locations) + VPN backup│
│ Active/Active load sharing │ 2 DX + ECMP + same communities │
│ Active/Passive failover    │ 2 DX + different communities   │
└──────────────────────────────┴─────────────────────────────────┘
```
