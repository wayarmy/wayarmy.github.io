## 1. Giới thiệu — Đường cao tốc thế hệ mới

Hãy tưởng tượng hệ thống giao thông qua các thời kỳ:

**HTTP/1.1 (TCP — 1 lane):**
- Đường 1 làn xe — từng xe đi lần lượt
- Muốn vượt? Phải đợi xe trước đi xong!
- Tắc 1 xe = TẮC CẢ ĐƯỜNG

**HTTP/2 (TCP — multi-lane illusion):**
- Vẫn là đường 1 làn, nhưng chia "ô" cho nhiều xe chạy xen kẽ
- NHƯNG nếu 1 xe hỏng giữa đường → vẫn chặn tất cả phía sau!
- (Head-of-line blocking tại TCP layer)

**HTTP/3 (QUIC — nhiều đường song song thật sự):**
- **Nhiều đường riêng biệt** chạy song song (independent streams)
- Xe hỏng trên đường 1? → Đường 2, 3 vẫn chạy bình thường!
- **Đường hầm bí mật** — mọi thứ được mã hóa (built-in TLS 1.3)
- **Chuyển làn mượt** — đổi từ WiFi sang 4G không bị ngắt (connection migration)
- **Lối tắt** — nếu đã đi lần trước, lần sau vào luôn không xếp hàng (0-RTT)

### QUIC là gì?

**QUIC** = Transport protocol chạy trên **UDP**, tích hợp sẵn:
- **TLS 1.3** encryption (mandatory)
- **Multiplexed streams** (no head-of-line blocking)
- **Connection migration** (change IP without reconnect)
- **0-RTT resumption** (instant reconnect)
- **Improved loss recovery** (better than TCP)

```
Protocol Stack Comparison:

HTTP/1.1 & HTTP/2:          HTTP/3:
┌──────────────┐            ┌──────────────┐
│  HTTP/1.1    │            │   HTTP/3     │
│  or HTTP/2   │            │  (RFC 9114)  │
├──────────────┤            ├──────────────┤
│  TLS 1.2/1.3│            │   QUIC       │
├──────────────┤            │  (RFC 9000)  │
│     TCP      │            │  +TLS 1.3    │
├──────────────┤            ├──────────────┤
│     IP       │            │     UDP      │
└──────────────┘            ├──────────────┤
                            │     IP       │
                            └──────────────┘
```

### Tại sao tạo QUIC? TCP có gì sai?

| TCP Problem | QUIC Solution |
|---|---|
| 3-way handshake + TLS = 2-3 RTT | Combined: 1 RTT (0-RTT for repeat) |
| Head-of-line blocking (1 stream lost → all blocked) | Independent streams — no HoL blocking |
| Connection tied to IP:port tuple | Connection ID — survive network switch |
| Ossification (middleboxes modify TCP) | Encrypted headers — can't be modified |
| Kernel implementation (hard to update) | Userspace — fast iteration |
| No built-in encryption | Mandatory TLS 1.3 |

### Ai dùng QUIC/HTTP3 hiện nay?

- **Google** (Chrome + YouTube + Search) — ~30% Google traffic
- **Facebook/Meta** (apps + web) — ~75% mobile traffic
- **Cloudflare** — all websites with HTTP/3 enabled
- **Akamai, Fastly** — CDN support
- **Apple** — iCloud, App Store
- **Microsoft** — Edge browser, Azure services

## 2. QUIC Architecture — Kiến trúc tổng thể

### Phép so sánh — Xe buýt vs Tàu cao tốc nhiều toa

**TCP + TLS + HTTP/2** = Xe buýt:
- 1 xe (connection) chở mọi khách (streams)
- Xe dừng vì 1 khách (packet loss) → TẤT CẢ phải đợi
- Xe hỏng → phải đợi xe mới (reconnect)

**QUIC** = Tàu cao tốc nhiều toa:
- Mỗi toa (stream) **độc lập** — khách 1 toa trễ không ảnh hưởng toa khác
- Đổi đường ray (network) → tàu vẫn chạy tiếp (connection migration)
- Đã đi 1 lần → lần sau lên luôn không cần vé mới (0-RTT)

### QUIC Connection Components

```
QUIC Connection:
┌─────────────────────────────────────────────────────────┐
│  Connection ID: 0x1a2b3c4d...                           │
│                                                         │
│  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐      │
│  │  Stream 0   │ │  Stream 4   │ │  Stream 8   │      │
│  │  (Control)  │ │  (Request1) │ │  (Request2) │      │
│  │             │ │             │ │             │      │
│  │  [frame]    │ │  [frame]    │ │  [frame]    │      │
│  │  [frame]    │ │  [frame]    │ │  [frame]    │      │
│  └─────────────┘ └─────────────┘ └─────────────┘      │
│                                                         │
│  Encryption: TLS 1.3 (AEAD — AES-128-GCM / ChaCha20)  │
│  Congestion Control: Cubic / BBR / custom              │
│  Flow Control: Per-stream + Connection-level           │
│                                                         │
│  Transport: UDP (port 443)                              │
└─────────────────────────────────────────────────────────┘
```

### QUIC Packet Structure

```
QUIC Long Header (used during handshake):
┌───────────────────────────────────────────────────┐
│ 1│1│ Type │ Rsv │ Pkt Num Len │ Version (32)     │
├───────────────────────────────────────────────────┤
│ DCID Len │ Destination Connection ID (0-20 bytes)│
├───────────────────────────────────────────────────┤
│ SCID Len │ Source Connection ID (0-20 bytes)     │
├───────────────────────────────────────────────────┤
│ Token Length │ Token (variable)                   │  ← Only in Initial
├───────────────────────────────────────────────────┤
│ Length (variable)                                 │
├───────────────────────────────────────────────────┤
│ Packet Number (1-4 bytes)                        │
├───────────────────────────────────────────────────┤
│ Payload (QUIC frames, encrypted)                 │
└───────────────────────────────────────────────────┘

QUIC Short Header (used after handshake — most packets):
┌───────────────────────────────────────────────────┐
│ 0│1│ Spin│Rsv│ Key Phase │ Pkt Num Len           │
├───────────────────────────────────────────────────┤
│ Destination Connection ID (variable)             │
├───────────────────────────────────────────────────┤
│ Packet Number (1-4 bytes)                        │
├───────────────────────────────────────────────────┤
│ Payload (encrypted QUIC frames)                  │
└───────────────────────────────────────────────────┘
```

### Connection ID — Key Innovation

```
TCP identifies connection by: (src IP, src port, dst IP, dst port)
  → Change ANY of these = broken connection!
  → WiFi → 4G: new IP → connection DEAD!

QUIC identifies connection by: Connection ID (opaque bytes)
  → Connection ID stays the same regardless of IP/port change
  → WiFi → 4G: different IP, SAME connection ID → continue!
  → Server uses Connection ID to find the right session

Connection ID is in QUIC header (not IP/UDP headers)
  → NAT, IP change don't affect QUIC connection identity
```

## 3. Connection Establishment — 1-RTT và 0-RTT

### Phép so sánh — Vào quán cà phê

**TCP + TLS 1.3 (2 RTT cho new connection):**
1. Vào quán → "Xin chào, tôi muốn ngồi" (SYN) → Đợi...
2. "Mời ngồi" (SYN-ACK) → "Cảm ơn" (ACK) → 1 RTT (TCP done)
3. "Tôi muốn kết nối bảo mật" (ClientHello) → Đợi...
4. "OK, đây là encryption keys" (ServerHello) → 2 RTT (TLS done)
5. BÂY GIỜ mới gọi được cà phê! (HTTP request)

**QUIC (1 RTT cho new, 0 RTT cho repeat):**
- Lần đầu: Vào quán → "Xin chào + tôi muốn bảo mật + cho cà phê luôn" → 1 RTT!
- Lần sau: "Nhớ tôi không? Cho cà phê như cũ!" → **0 RTT**! (instant!)

### 1-RTT Handshake (First Connection)

```
Client                                          Server
  │                                               │
  │  Initial Packet (Long Header):                │
  │  ├ CRYPTO frame (TLS ClientHello)             │
  │  ├ Supported versions, cipher suites          │
  │  ├ Key share (Diffie-Hellman public key)      │
  │  └ Transport parameters (streams, flow ctrl)  │
  │                                               │
  │──────── UDP Datagram ────────────────────────→│
  │                                               │
  │                    Initial + Handshake Packets:│
  │                    ├ CRYPTO (ServerHello)      │
  │                    ├ Certificate              │
  │                    ├ CertificateVerify        │
  │                    ├ Finished                 │
  │                    └ Transport parameters     │
  │                                               │
  │←──────── UDP Datagram ───────────────────────│
  │                                               │
  │  Handshake Packet:                            │
  │  ├ CRYPTO (Finished)                          │
  │  ├ ★ Application data can be sent NOW! ★      │
  │                                               │
  │──────── UDP Datagram ────────────────────────→│
  │                                               │
  │       [ESTABLISHED — after 1 RTT total]       │
  
Compare with TCP + TLS 1.3:
  SYN → SYN-ACK → ACK + ClientHello → ServerHello... = 2 RTT minimum!
  
QUIC saves 1 RTT because crypto and transport handshake are COMBINED!
```

### 0-RTT Resumption (Repeat Connection)

```
Sau first connection, server cung cấp "session ticket" cho client.
Lần sau client reconnect:

Client                                          Server
  │                                               │
  │  Initial Packet:                              │
  │  ├ CRYPTO (ClientHello + PSK identity)        │
  │  ├ ★ 0-RTT Application Data (early data) ★   │
  │  │   (Encrypted with PSK-derived keys)        │
  │  └ Transport parameters                       │
  │                                               │
  │──────── UDP Datagram ────────────────────────→│
  │                                    Server can │
  │                                    process    │
  │                                    request    │
  │                                    IMMEDIATELY│
  │                                               │
  │←──────── Response ──────────────────────────│
  │                                               │

0-RTT = Client gửi data NGAY trong packet đầu tiên!
  - Không cần chờ handshake hoàn tất
  - Giảm latency đáng kể cho repeat visits
  - HTTPS website load ~30% nhanh hơn cho returning users
```

**0-RTT Security Considerations:**
```
⚠️ 0-RTT data có thể bị REPLAY ATTACK!
  - Attacker capture 0-RTT packet → resend → server processes twice!
  - Mitigation:
    - Only use 0-RTT for IDEMPOTENT requests (GET, not POST)
    - Server-side replay protection (single-use tickets, strike registers)
    - Limited by transport parameters (max data in 0-RTT)
```

## 4. Multiplexed Streams — No Head-of-Line Blocking

### Phép so sánh — Hàng rau vs Hàng thịt ở siêu thị

**HTTP/2 over TCP (shared queue):**
- Tất cả khách xếp **1 hàng** (single TCP connection)
- Khách #3 trả tiền lâu → #4, #5, #6 phải đợi! (HoL blocking)
- Dù có "express lane" (stream priority) → vẫn chung 1 queue

**HTTP/3 over QUIC (independent queues):**
- **Mỗi quầy** (stream) có queue riêng!
- Quầy rau chậm → quầy thịt vẫn phục vụ bình thường!
- Stream 4 lost packet → CHỈ Stream 4 chờ retransmit
- Stream 8, 12 tiếp tục nhận data bình thường!

### Head-of-Line Blocking Problem (TCP)

```
HTTP/2 over TCP — Multiple streams share 1 TCP connection:

TCP byte stream: [S1][S2][S3][S1][S2][S4][S3]...
                         ↑
                    Packet LOST!

TCP behavior:
  - TCP sees loss at byte position X
  - TCP retransmits byte X
  - ALL bytes after X are HELD in receive buffer
  - Application cannot read ANY stream until X is recovered!
  
  Stream 1: blocked! (waiting for retransmit)
  Stream 2: blocked! (even though its data is in buffer!)
  Stream 3: blocked!
  Stream 4: blocked!
  
  One lost packet → ALL streams delayed!
  On 2% loss rate: HTTP/2 can be SLOWER than HTTP/1.1!
```

### QUIC Solution — Independent Stream Recovery

```
QUIC — Each stream has independent byte offset:

Stream 0: [frame 0-100] [frame 100-200] [frame 200-300]
Stream 4: [frame 0-500] [frame 500-1000] ← packet lost!
Stream 8: [frame 0-300] [frame 300-600] [frame 600-900]

QUIC behavior:
  - Packet containing Stream 4 frame [500-1000] lost
  - QUIC retransmits ONLY that stream's data
  - Stream 0 and Stream 8: DELIVERED IMMEDIATELY to app!
  - Only Stream 4 waits for retransmit!

  Stream 0: ✓ delivered (no blocking)
  Stream 4: ⏳ waiting for retransmit
  Stream 8: ✓ delivered (no blocking)
  
  Result: 1 lost packet → only 1 stream affected!
```

### QUIC Stream Types

```
Stream ID encoding (62-bit):
  - Bit 0: Initiator (0 = client-initiated, 1 = server-initiated)
  - Bit 1: Directionality (0 = bidirectional, 1 = unidirectional)

Stream types:
  0x0: Client-initiated, Bidirectional (0, 4, 8, 12...)
  0x1: Server-initiated, Bidirectional (1, 5, 9, 13...)
  0x2: Client-initiated, Unidirectional (2, 6, 10, 14...)
  0x3: Server-initiated, Unidirectional (3, 7, 11, 15...)

HTTP/3 usage:
  Client request:  Stream 0, 4, 8, 12... (client bidi)
  Server push:     Stream 1, 5, 9... (server bidi) [deprecated]
  Control stream:  Stream 2 (client uni), Stream 3 (server uni)
  QPACK encoder:   Stream 6 (client uni), Stream 7 (server uni)
  QPACK decoder:   Stream 10 (client uni), Stream 11 (server uni)
```

### Flow Control — Dual Level

```
QUIC has TWO levels of flow control:

1. Connection-level:
   MAX_DATA frame: "Total bytes for ALL streams ≤ X"
   
2. Per-stream:
   MAX_STREAM_DATA frame: "Bytes for THIS stream ≤ Y"

Example:
  Connection limit: 10 MB total
  Stream 4 limit: 2 MB
  Stream 8 limit: 5 MB
  
  Stream 4 can send up to 2 MB
  Stream 8 can send up to 5 MB
  Total across all streams ≤ 10 MB

Flow control update:
  Receiver sends MAX_DATA / MAX_STREAM_DATA when buffer freed
  Similar to TCP window update, but per-stream!
```

## 5. Connection Migration — Đổi mạng không mất kết nối

### Phép so sánh — Số điện thoại di động

**TCP = Điện thoại bàn:**
- Gắn vào 1 ổ cắm (IP address)
- Muốn đổi ổ → phải NGẮT cuộc gọi, gọi lại!
- Đổi từ office → home = connection mới hoàn toàn

**QUIC = Điện thoại di động:**
- Di chuyển thoải mái — số không đổi (Connection ID)
- Từ WiFi → 4G → WiFi: cuộc gọi TIẾP TỤC, không ngắt!
- Số ID giữ nguyên dù thay đổi mạng (IP)

### Connection Migration hoạt động

```
Scenario: User đang xem YouTube qua WiFi, rời khỏi nhà (chuyển sang 4G)

Với TCP:
  1. WiFi: TCP conn = (192.168.1.100:54321 → 216.58.214.206:443)
  2. Rời WiFi → IP thay đổi thành 4G: 100.64.1.50
  3. TCP tuple (100.64.1.50:xxxxx → 216.58.214.206:443) ≠ old tuple
  4. TCP connection BROKEN! Must reconnect + TLS handshake again!
  5. Video buffers, app shows "reconnecting...", 2-3 seconds lost

Với QUIC:
  1. WiFi: QUIC conn ID = 0xABCD1234 (IP = 192.168.1.100)
  2. Rời WiFi → IP đổi sang 4G: 100.64.1.50
  3. Client gửi packet từ new IP, SAME connection ID: 0xABCD1234
  4. Server: "Connection ID 0xABCD1234? Ah, cùng client! Continue!"
  5. Path validation (verify new path works)
  6. Video CONTINUES without interruption! ✓
```

### Path Validation

```
Khi migration xảy ra, server cần verify new path (chống spoof):

1. Client sends packet from new IP with same Connection ID
2. Server receives: "New IP? Need to validate!"
3. Server sends PATH_CHALLENGE frame (random 8-byte token)
4. Client must respond with PATH_RESPONSE (same token) from NEW IP
5. If valid → migration accepted, continue on new path
6. Server may also probe old path (detect NAT rebinding vs real migration)

Security:
  - PATH_CHALLENGE prevents reflection/amplification attacks
  - Attacker can't just spoof Connection ID to redirect traffic
  - Both paths validated before full migration
```

### Multipath QUIC (Future — Draft)

```
Multipath = use MULTIPLE networks simultaneously!

Current: Migration = switch from path A to path B
Future:  Multipath = use path A AND path B at the same time!

Example:
  WiFi (fast, unreliable at edge) + 4G (slower, more reliable)
  QUIC sends packets over BOTH → better throughput + reliability
  
  Stream priorities can determine which path:
    Video → WiFi (bandwidth)
    Control → 4G (reliability)
    
Draft: draft-ietf-quic-multipath
```

## 6. QUIC Loss Recovery và Congestion Control

### Loss Detection — Better than TCP

```
TCP problems with loss detection:
  1. Retransmission ambiguity:
     TCP retransmits with SAME sequence number
     → ACK arrives → for original or retransmit? Can't tell!
     → RTO calculation inaccurate

  2. Sequence number ≠ transmission order:
     Retransmit reuses old seq → confuses RTT measurement

QUIC solutions:
  1. Unique packet numbers (always increasing):
     Original:    Packet #5 (seq monotonically increases)
     Retransmit:  Packet #12 (NEW number, same stream offset)
     → ACK for #5 = definitely for original
     → ACK for #12 = definitely for retransmit
     → Clean RTT measurement!

  2. Explicit ACK delay:
     QUIC ACK frames include "ACK Delay" field
     → Receiver tells sender how long it held the ACK
     → Better RTT calculation (subtract deliberate delay)

  3. Larger ACK blocks:
     QUIC ACKs can acknowledge up to 256 ranges
     (TCP SACK: limited to ~3-4 blocks in options)
     → Better information about what was received
```

### QUIC ACK Frame

```
ACK Frame:
┌────────────────────────────────────────┐
│ Largest Acknowledged (variable-length) │  ← Highest packet # received
│ ACK Delay (variable-length)            │  ← How long receiver waited
│ ACK Range Count (variable-length)      │  ← Number of gaps
│ First ACK Range (variable-length)      │  ← Packets before largest
│ [ACK Range repeats...]                 │  ← Gap + Range pairs
│   Gap (variable-length)                │
│   ACK Range (variable-length)          │
└────────────────────────────────────────┘

Example: Received packets 1-5, 8-10, 15-20
  Largest Acknowledged: 20
  First ACK Range: 5 (= packets 15-20)
  Gap: 4 (= packets 11-14 missing)
  ACK Range: 2 (= packets 8-10)
  Gap: 2 (= packets 6-7 missing)
  ACK Range: 4 (= packets 1-5)
```

### Congestion Control

```
QUIC supports PLUGGABLE congestion control:
  - Default: similar to TCP NewReno/CUBIC
  - Can use: BBR, CUBIC, Copa, custom
  - Congestion window operates at CONNECTION level (not per-stream)
  - Implementations can innovate without OS kernel updates!

Google's QUIC: Uses BBR (Bottleneck Bandwidth and RTT)
  - Model-based (not purely loss-based)
  - Better throughput on lossy networks
  - Lower latency under congestion
  
Cloudflare QUIC: Uses CUBIC (similar to Linux TCP)
  - Well-understood behavior
  - Fair sharing with TCP flows
```

## 7. HTTP/3 — HTTP over QUIC

### HTTP/3 vs HTTP/2 — Key Differences

| Feature | HTTP/2 (over TCP) | HTTP/3 (over QUIC) |
|---|---|---|
| Transport | TCP + TLS | QUIC (UDP + built-in TLS) |
| HoL blocking | ✗ TCP-level blocking | ✓ No HoL blocking |
| Connection setup | 2-3 RTT | 1 RTT (0-RTT repeat) |
| Header compression | HPACK | QPACK |
| Server push | Supported | Deprecated (RFC 9218) |
| Prioritization | Tree-based (complex) | Urgency + incremental (simpler) |
| Migration | ✗ Impossible | ✓ Connection ID |

### HTTP/3 Frame Types

```
HTTP/3 frames (inside QUIC streams):

┌─────────────┬──────────────────────────────────┐
│ Frame Type  │ Purpose                          │
├─────────────┼──────────────────────────────────┤
│ DATA (0x00) │ Request/Response body            │
│ HEADERS     │ Request/Response headers         │
│ (0x01)      │ (QPACK compressed)              │
│ CANCEL_PUSH │ Cancel server push              │
│ (0x03)      │                                  │
│ SETTINGS    │ Connection configuration         │
│ (0x04)      │                                  │
│ PUSH_PROMISE│ Server push (deprecated)        │
│ (0x05)      │                                  │
│ GOAWAY      │ Graceful shutdown               │
│ (0x07)      │                                  │
└─────────────┴──────────────────────────────────┘
```

### QPACK — Header Compression for HTTP/3

```
HTTP/2 HPACK problem:
  - HPACK uses dynamic table that MUST be synchronized
  - Over TCP: sequential delivery → table always in sync
  - Over QUIC: streams are independent → table might be out-of-sync!
  
  Stream 4 encodes header using entry #5 in dynamic table
  Stream 8 hasn't received the entry yet → DECODE FAILURE!

QPACK solution:
  - Separate unidirectional streams for table updates
  - Encoder stream: sends table updates
  - Decoder stream: acknowledges table updates
  - Headers can reference static table immediately
  - Dynamic table references only AFTER acknowledged
  
  Static table: 99 pre-defined common headers
    index 0: :authority
    index 1: :path /
    index 2: age 0
    ...
    index 98: x-content-type-options nosniff
```

### HTTP/3 Connection Lifecycle

```
1. Discovery (Alt-Svc header):
   Client makes HTTP/2 request to example.com
   Server response includes:
     Alt-Svc: h3=":443"; ma=86400
     ("HTTP/3 available on UDP port 443, valid for 24h")
   
   Client: "Next time, I'll try HTTP/3!"

2. QUIC Handshake (1-RTT):
   Client → QUIC Initial (TLS ClientHello, ALPN=h3) → Server
   Server → QUIC Handshake (ServerHello, Cert...) → Client
   Connection established!

3. HTTP/3 Setup:
   Client creates control stream (unidirectional, stream 2)
   Server creates control stream (unidirectional, stream 3)
   Exchange SETTINGS frames

4. Request/Response:
   Client opens bidirectional stream (stream 0):
     HEADERS frame: GET / HTTP/3
   Server responds on same stream:
     HEADERS frame: 200 OK
     DATA frame: <html>...</html>
   Stream closed (FIN)

5. Subsequent requests: new streams (4, 8, 12...)
   All multiplexed on SAME QUIC connection!
```

## 8. QUIC Deployment — Thực tế triển khai

### Server-side Implementation

```bash
# Popular QUIC implementations:

# nginx (quic branch, mainline since 1.25):
server {
    listen 443 quic reuseport;
    listen 443 ssl;
    
    ssl_certificate /etc/ssl/cert.pem;
    ssl_certificate_key /etc/ssl/key.pem;
    
    # Advertise HTTP/3
    add_header Alt-Svc 'h3=":443"; ma=86400';
    
    # QUIC transport parameters
    quic_retry on;     # Stateless retry (DDoS protection)
}

# Caddy (built-in HTTP/3 support):
# Just works! Caddy enables HTTP/3 by default
caddy reverse-proxy --from example.com --to localhost:8080

# Cloudflare (automatic):
# Enable in dashboard: Speed → Protocol Optimization → HTTP/3
```

```
Cloudflare measurements:
  - TTFB (Time to First Byte): 12% improvement (median)
  - High-loss networks (>2%): up to 30% improvement
  - Connection migration: seamless on mobile

Facebook measurements:
  - Request errors: 6% reduction
  - Tail latency (p99): 20% improvement
  - Mobile: significant improvement on poor networks
```

### Firewall và NAT Considerations

```
⚠️ QUIC challenges:

1. Firewall blocking UDP/443:
   - Some enterprise firewalls block all UDP
   - Solution: fallback to TCP/TLS (Alt-Svc mechanism)
   - Chrome: tries QUIC, falls back to TCP if UDP blocked

2. NAT timeout:
   - UDP NAT mappings timeout faster than TCP (30-120s vs hours)
   - QUIC sends PING frames to keep NAT mapping alive
   - Configurable idle timeout in transport parameters

3. Network monitoring:
   - QUIC encrypts nearly everything (including headers!)
   - Deep packet inspection tools can't see HTTP content
   - Solution: enterprise QUIC interception (split-tunnel)

4. Load balancer routing:
   - Traditional LB uses 5-tuple → QUIC changes IP!
   - Solution: QUIC-aware LB reads Connection ID
   - CID encoding: LB puts routing info in Connection ID
```

## 9. QUIC Security — Built-in Protection

### Encryption — Always On

```
QUIC encrypts EVERYTHING:
  - Payload: always encrypted (AEAD)
  - Most header fields: encrypted
  - Packet number: encrypted
  - Connection ID: visible but opaque (no meaning to observers)

Only visible to middleboxes:
  - UDP source/dest IP and port
  - QUIC version (in Initial packets)
  - Connection ID (opaque bytes)
  - Spin bit (1 bit for passive RTT measurement)
  
TCP comparison — visible to middleboxes:
  - Sequence numbers → can track
  - Window size → can modify
  - Flags (SYN/FIN/RST) → can modify
  - Payload (if no TLS) → can inspect/modify
```

### Anti-Amplification

```
Before address validation, server limited to 3× bytes received:
  - Client sends 1200-byte Initial
  - Server can respond with at most 3600 bytes
  - Prevents server being used as amplifier in DDoS

Retry mechanism:
  1. Client → Initial → Server
  2. Server → Retry Token (stateless) → Client
  3. Client → Initial + Retry Token → Server (proves IP is real)
  4. Server → continue handshake

Retry prevents amplification with spoofed source IPs
```

### Key Update — Rotate Keys Without Reconnect

```
QUIC supports in-connection key rotation:
  - Both endpoints can update encryption keys
  - Key Phase bit in header signals new key
  - Old keys kept temporarily (for out-of-order packets)
  - No connection interruption!
  
Benefits:
  - Limit damage if key compromised
  - Comply with key rotation policies
  - Forward secrecy within connection
```

## 10. QUIC vs TCP — Khi nào dùng gì?

### Decision Matrix

```
Use QUIC/HTTP3 when:
  ✓ Web browsing (most common use case)
  ✓ Mobile apps (connection migration)
  ✓ High-latency connections (satellite, mobile)
  ✓ Lossy networks (WiFi, cellular)
  ✓ Multiple concurrent requests (multiplexing)
  ✓ Privacy-sensitive (encrypted headers)
  ✓ Repeat visitors (0-RTT benefit)

Stick with TCP when:
  ✓ Enterprise network blocks UDP
  ✓ Need deep packet inspection
  ✓ Legacy application protocol (SSH, SMTP...)
  ✓ Very long connections (database)
  ✓ Kernel-level reliability needed
  ✓ Hardware offload available (TCP offload engines)
```

```
│                                                         │
```
